# Agent contributor rules
Operate only inside this repository. Never inspect or modify unrelated repositories, services, databases, containers or customer workloads. Maintain SPRINTS.md and BACKLOG.md for scope changes. Add an issue for new features, and attach each PR to an active-sprint issue or backlog item (break/fix exempt). Validate tests and docs before opening PRs. Prefer standard-library or license-audited open source. Do not store secrets in Git, contact prospects, provision cloud resources, or pay for APIs. Never merge unreviewed changes. Leave running containers and persistent volumes intact unless owned by this project. Include PR URL and test evidence in progress updates.

## README badge convention

The source of truth is [madmallard-repository-standards](https://github.com/drakeg/madmallard-repository-standards), when it publishes actionable standards; this local policy applies until then. Maintain a compact Shields.io badge group immediately beneath the root README title, preferably two or three rows. Inspect actual manifests, dependency lockfiles, Dockerfiles, deployment configuration, LICENSE, releases, and GitHub Actions before changing a badge. Never invent technologies, versions, workflow success, security checks, deployments or releases. Version badges require verified configuration; CI, release, license and repository-statistic badges must be dynamic. Include release, security, or deployment badges only when the corresponding capability exists. Make badges link to verified configuration or relevant pages. Preserve all existing README content outside the badges. Run `python3 scripts/validate_badges.py` with normal documentation checks and update the validator when documented badge conventions change.

## Mad Mallard execution standard (2026-11-19)
- Follow **Build → Deploy → Test → Fix → Redeploy → Continue** during authorized development sessions. Do not assume a successful build or PR merge proves the user workflow is working; verify the running application.
- Keep the Docker Compose test environment operational and, when safe, bound to the configured LAN interface. Preserve volumes and unrelated containers. Never expose unauthenticated dashboards or credentials to the public internet.
- Keep `README.md`, `SPRINTS.md`, `BACKLOG.md`, `RELEASES.md` and contribution documentation aligned with actual implementation. Record planned and completed Sprint work with clear acceptance checks. Move to the next ready task rather than stopping for ordinary milestones.
- Inspect real dependency, Docker, CI, security and deployment configurations before adding/updating badges. Prefer dynamic GitHub badges for Actions, releases, licensing, issues and PRs; never hardcode green status. Run badge validation in CI when applicable.
- Prioritize the **Five-Job Automation Watchdog Setup** SMB offer: detectable missed/import failures, trustworthy output validation, simple installation, a usable dashboard and a recovery runbook. Treat the proposed $399 pilot as an unvalidated pricing hypothesis; do not invent customer demand or outreach results.
- Use reviewable branches, PRs, and passing CI. Respect required reviews and branch protections. Report PR URLs, tests, deployment status and blockers. Only request explicit authorization for destructive work, paid services, production changes or consequential decisions.
- Consult `drakeg/madmallard-repository-standards` as the upstream standards reference when actionable material is present, without coupling this repository to its services or contradicting this app's isolation constraints.
